This page lists known issues, limitations and workarounds when working with the TED Open Data Service.

The SPARQL snippets on this page are partial patterns. They use the `epo:` prefix, which is declared as `PREFIX epo: <http://data.europa.eu/a4g/ontology#>`.

== Notices

=== Notice count: count publication numbers, not `?notice`

Counting distinct notices using `?notice` can give a lower number than counting distinct notice publication numbers. This is because a notice is currently identified by its UUID without the version number, and the same UUID can be used by more than one published notice. This issue will be fixed in the future.   

For example, the notice with publication number https://ted.europa.eu/en/notice/-/detail/00176184-2026[00176184-2026] has the notice UUID `a2add710-2c39-45f3-ae16-4edf2f5c191c` (without the version number).

**Workaround:** Count distinct publication numbers to get the number of distinct notices.

[source,sparql]
----
# Assuming your query pattern is as below
GRAPH ?g {
  ?notice a epo:Notice ;
          epo:hasNoticePublicationNumber ?noticePublicationNumber ;
          epo:hasPublicationDate ?pubDate .
}

# Use this
(COUNT(DISTINCT ?noticePublicationNumber) AS ?noticeCount)

# NOT this
(COUNT(DISTINCT ?notice) AS ?noticeCount)
----

== ePO

=== Versions of ePO used: 4.2 (eForms) and 3.1 (standard forms)

The current eForms data (triples) in the TED Open Data Service is processed according to version 4.2 of ePO (the eProcurement Ontology), and the standard forms data according to version 3.1. The latest version of ePO is 5.2. Work is in progress to reprocess the data to match it.


=== Some relationships are not available in the data

Not all of the relationships defined in ePO are available in the data in the TED Open Data Service. To check which relationships are available, inspect a notice and look at its triples.

=== Missing direct relationship between contract and notice or buyer

There is no direct relationship in the triples between a contract (`epo:Contract`) and its notice or buyer. The indirect relationship is through the lot.

=== Winning tender

There is no indicator of whether a tender is a winning tender. A tender linked to a contract (`epo:Contract`) is considered the winning tender.

=== Class name spelling: `Organization` vs `OrganisationGroup`

Class names use different spellings depending on the vocabulary they come from:

* `org:Organization` (US spelling) comes from the W3C Organization Ontology (`http://www.w3.org/ns/org#`).
* `epo:OrganisationGroup` (UK spelling) comes from ePO. It is a subclass of `org:Organization`.

Use the exact spelling of each class in your queries. 

=== Property name spelling: `isSubmitedBy`

In ePO 4.2, the property linking a tender to its tenderer is spelled `epo:isSubmitedBy` (single 't'). Queries that use `isSubmittedBy` will not match the data.

**Workaround:** Use `epo:isSubmitedBy` (with single 't') in your queries.

[source,sparql]
----
# Use this
?tender epo:isSubmitedBy ?tenderer .

# NOT this (won't match the data)
# ?tender epo:isSubmittedBy ?tenderer .
----

== Query performance limitations

=== Timeout on large date ranges

Queries spanning more than 6 months of data may time out, especially when combined with multiple joins (for example, notice → lot → contract → tender → tenderer).

=== No caching of results

The results of executed SPARQL queries are not cached. Every time a query is run, even if it is the same query, the data is fetched from the triplestore. 

== Data availability and quality

=== Standard forms (or non-eForms) data not fully available

Not all of the standard forms data is available within the named graphs. For the period covered, see xref:ROOT:data_availability.adoc[Current data availability]. Work is in progress to map and load the remaining standard forms data.

* *Querying:* the queries in the *Explore* (Query Library) tab work only for eForms. To fetch standard forms data, additional logic is required. For example, the publication date is a string for standard forms, but a date for eForms.
* *Inspecting:* standard forms notices can be inspected. For example, try publication number 516873-2023.

=== Currencies

Financial values are only available in their original currencies, as published in the notices. This prevents users from comparing financial values across notices.

**Workaround:** Use the currency-conversion snippet, which provides exchange rates: type `currency` in the query editor to insert it. The snippet uses the latest exchange rates, not the rates on the publication date of the notice. For more details, refer to the help page of the https://data.ted.europa.eu/[TED Open Data Service].

In the future, the TED Open Data Service may provide financial values in euros in addition to the original currency.

=== Data quality issues

Data quality issues in the source XML files are carried over to the triples in the TED Open Data Service. No data cleansing is done when transforming XML into RDF triples.

=== Missing winner information in some notices

Some result notices do not include information about the winning tenderer. This means queries that require winner details may return fewer results than expected.

**Workaround:** Use `OPTIONAL` when fetching winner information to avoid losing the entire notice from results.

[source,sparql]
----
OPTIONAL {
  ?tenderer a epo:Tenderer ;
            epo:playedBy ?org .
  ?org epo:hasLegalName ?winnerName .
}
----
